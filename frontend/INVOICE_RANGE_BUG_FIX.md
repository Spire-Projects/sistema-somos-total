# Invoice Range Duplication Bug Fix

## Problem Description
Multiple terminals were grabbing the same recycled range (12-20) and creating duplicates. When one terminal completed a range, other terminals would immediately recycle the same range, causing:

1. **Duplicate ranges**: Multiple active ranges with identical start-end numbers
2. **Number conflicts**: Same invoice numbers being generated by different terminals
3. **Infinite loops**: Completed ranges being immediately recreated

## Root Causes Identified

### 1. Race Condition in Range Creation
- Multiple terminals could simultaneously call `findRecyclableNumbers()`
- All would get the same recyclable range (e.g., 12-20)
- All would create identical ranges without validation

### 2. No Duplicate Range Validation
- No check to prevent creating ranges with identical start-end numbers
- The system allowed multiple active ranges with the same number sequence

### 3. Immediate Recycling
- Completed ranges became immediately available for recycling
- No delay or cooling-off period
- Led to rapid recycling loops

## Fixes Implemented

### 1. Added Range Existence Validation
**File**: `numberInvoiceRange.repository.ts`
- Added `findExistingRangeByNumbers()` method
- Checks if a range with specific start-end numbers already exists and is active

```typescript
async findExistingRangeByNumbers(startNumber: number, endNumber: number): Promise<NumberInvoiceRangeDocument | null> {
  // Buscar cualquier rango que tenga exactamente los mismos números de inicio y fin
  const existingRange = await db.number_invoice_ranges.findOne({
    selector: {
      'range.0': startNumber,
      'range.1': endNumber,
      active: true // Solo considerar rangos activos
    }
  }).exec();
  return existingRange ? existingRange.toJSON() as NumberInvoiceRangeDocument : null;
}
```

### 2. Enhanced Range Creation Logic
**File**: `InvoiceNumberService.ts`
- Added validation before creating any range
- Falls back to alternative recyclable numbers if primary choice already exists
- Double-check validation before final range creation

Key improvements:
- **Primary validation**: Check if preferred recyclable range already exists
- **Alternative search**: Try other recyclable ranges if primary is taken
- **Final validation**: Double-check before actual creation
- **Graceful fallback**: Use existing active ranges if creation fails

### 3. Improved Recycling Logic
**File**: `numberInvoiceRange.repository.ts`
- Added 5-minute delay before ranges become recyclable after completion
- Added protection against recycling currently active ranges
- Better filtering of recyclable candidates

```typescript
const RECYCLING_DELAY = 5 * 60 * 1000; // 5 minutos de delay antes de reciclar

// Solo reciclar rangos completados después del delay
{ 
  status: NumberInvoiceStatus.COMPLETED, 
  expiredAt: { $lt: now - RECYCLING_DELAY } // Delay adicional para rangos completados
}
```

### 4. Enhanced Logging
- Added detailed console logging for debugging
- Track when ranges are skipped due to duplication
- Log alternative range selection process

## Prevention Mechanisms

### 1. **Duplicate Prevention**
- Every range creation now validates uniqueness
- Multiple fallback strategies prevent creation failures

### 2. **Race Condition Mitigation**
- Validation happens at multiple points during creation
- Alternative range selection reduces conflicts

### 3. **Recycling Delays**
- 5-minute cooling period for completed ranges
- Prevents immediate recycling loops
- Additional active range checks
